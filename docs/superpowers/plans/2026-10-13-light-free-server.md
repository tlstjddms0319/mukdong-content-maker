# 무료 서버 가볍게 하기 + 일러스트 음식 맛있어 보이게 — 계획서

작성: 2026-10-13 · 대상: Render 무료 인스턴스(메모리 512MB, 싱가포르) · 상태: 계획(아직 구현 안 함)

## 왜 하는가

- **서버**: 무료 서버는 메모리가 512MB뿐이다. 카드 두 장을 동시에 그리면 약 218MB를 써서(`render/renderLock.ts` 측정), 다른 일과 겹치면 프로세스가 죽고 앞단이 520을 돌려준다(2026-10-13 운영). #147~#151에서 막으려 했지만 아래 '가장 큰 구멍'이 남아 있다.
- **일러스트**: 그림 콘셉트(#143)로 만든 장에서 홍어회·홍어찜이 보라색 연기와 찡그린 얼굴 캐릭터로 그려진다. 사장님 지적은 "맛없어 보인다"이다. 2026-10-13 게시물 예시: "홍어찜은 왜 회보다 향이 훨씬 강할까?"

## 할 일 (우선순위 순)

### 0단계 — 바로 고칠 구멍 (반나절, 효과 가장 큼)

1. **생성 API에 그리기 순서 대기 걸기**: `route.ts`의 `composeSlideImage`가 `composeSlideCard`를 `withRenderLock`으로 감싸게 한다. `photoWindow.ts`, 무료 카드(`renderFreeCard.ts`), 가게 홍보 카드(`storeCard.ts`)의 sharp 작업도 같은 대기에 넣는다.
   - 기대: 동시 그리기 피크가 약 218MB에서 약 110MB로, 대략 절반이 된다.
   - 시험: 두 요청을 동시에 보내도 그리기 구간이 겹치지 않는지 본다.
2. **메모리 기록 넣기**: 카드 한 장을 그리기 전과 후에 `rss`·`heapUsed`·`external`을 로그에 한 줄씩 남긴다. 운영 로그로 실제 피크를 확인해야 다음 단계를 고를 수 있다.
3. **가벼운 헬스 체크**: `/api/health`를 만들어 페이지 렌더 없이 200만 돌려주게 한다. `render.yaml`의 `healthCheckPath`도 바꾼다.

### 1단계 — 메모리 줄이기 (1~2일)

4. **글꼴 필요한 것만 읽기**
   - `preloadFonts`가 30개를 한꺼번에 읽지 않게 한다. 그리는 모양이 쓰는 글꼴만 처음 쓸 때 읽는다.
   - 거의 안 쓰는 큰 글꼴은 정리한다. 감자꽃 12.6MB, 고운바탕 8MB×2, 고운돋움 7MB, 갈무리 5.4MB가 후보다.
   - 쓰는 글자만 남긴 서브셋 글꼴(한글 2,350자 + 영숫자)로 바꾸면 크기가 1/3~1/5로 준다. pyftsubset으로 빌드할 때 만든다.
   - 기대: 글꼴 메모리와 이미지 용량에서 수십 MB.
5. **같은 그림 한 번만 디코드**: `route.ts`에서 AI 그림을 한 번만 버퍼로 만들어 표지 검사·누끼·합성이 함께 쓰게 한다. URL은 한 번만 내려받는다.
6. **다시 그리기 횟수 줄이기**: 자동 검수 재시도를 최대 3번에서 2번으로 줄인다. 재시도 전에는 앞 시도의 버퍼를 놓아 준다.
7. **크기 제한 없는 캐시에 상한 걸기**: `grainCache`, `mascotCache`, `storeCard.fitted`에 `cachedLayer`와 같은 LRU(MB·개수) 상한을 건다.
8. **sharp 스레드 1개**: 무료 서버(공유 CPU)에서는 스레드 2개가 빠르지 않다. `SHARP_CONCURRENCY=1`로 시험해 메모리와 시간을 비교한다.

### 2단계 — 응답·저장 가볍게 (1~2일)

9. **base64 대신 파일 주소**: 밑그림(1440px)과 표지 참고(1024px)를 JSON에 base64로 싣지 않는다. 저장소(Supabase Storage나 `DATA_DIR`)에 두고 주소만 돌려준다. 응답이 수 MB에서 수 KB로 준다.
10. **사진 보관함 목록 가볍게**: 메타 정보(이름·크기·품질)와 미리보기를 따로 저장해, 목록은 메타만 읽게 한다. 미리보기는 필요한 화면에서만 읽는다.
11. **예약 게시 1분 주기**: GitHub 크론이 이미 1시간마다 깨운다. 서버 안 루프는 5분으로 늘리거나, 예약 글이 있을 때만 돌게 한다.

### 3단계 — 실행 설정 (반나절)

12. **실행 힙 상한 다시 걸기**: 빌드는 지금처럼 넉넉하게 하고, 실행만 `startCommand: NODE_OPTIONS=--max-old-space-size=300 npm start`로 둔다. 빌드에 영향이 없게 `startCommand` 안에서만 정한다(#147 실패 원인을 피함). 상한에 닿으면 Node가 먼저 GC를 세게 돌려 프로세스가 죽는 일을 줄인다.
13. **`output: "standalone"`** 으로 실행 파일 크기와 부팅 메모리를 줄인다. 글꼴·디자인 파일은 지금의 `outputFileTracingIncludes`로 같이 묶인다.
14. (선택) 카드 그리기를 브라우저로 옮기는 안은 비용이 커서 이번에는 하지 않는다. 서버 피크가 1~3단계 뒤에도 400MB를 넘으면 그때 다시 본다.

### 확인 방법

- 로컬: `node --max-old-space-size=300`으로 띄워 5장 게시물 2개를 동시에 만들고, 0단계에서 넣은 메모리 로그로 피크를 잰다.
- 운영: 배포 뒤 하루 동안 Render 로그에서 카드 그리기 피크 `rss`가 512MB의 70%(약 360MB) 아래인지, 520이 다시 나는지 본다.
- 시험: 기존 1100여 개 + 순서 대기 겹침 시험 + 캐시 상한 시험.

## 일러스트 음식이 맛없어 보이는 문제

### 원인 (코드에서 확인)

- 그림 콘셉트 '캐릭터 대결'은 "음식을 의인화한 캐릭터"이고 만화 얼굴을 허용한다(`concepts.ts:17,77`). 화풍 문장은 "expressive cartoon faces … Not a photograph"이다(`style.ts:43-48`). 그림 지시에도 "Cartoon character faces are fine"이 들어간다(`openaiRequest.ts:219-221`).
- 그래서 **먹는 음식 자체에 얼굴**이 생기고, 냄새를 보라색 연기로 그려 식욕을 떨어뜨린다.
- 콘셉트를 고르면 화풍 기준에서 "실제 음식 사진 질감"이 빠진다(`concepts.ts:119` `applyConcept`).
- 콘셉트 화면은 AI 추천 콘셉트를 먼저 골라 둔다. '실사'가 기본이 아니다(`concepts/route.ts:26`).
- 사장님이 직접 넣은 사진은 바뀌지 않는다. 콘셉트는 AI로 그리는 게시물에서만 쓴다.

### 고칠 방향

1. **먹는 음식에는 얼굴을 그리지 않는다**
   - 캐릭터·만화 콘셉트에서 얼굴과 표정은 접시 밖의 작은 마스코트(가게 홍어 캐릭터)나 사람에게만 준다.
   - 접시 위 음식은 실제 모양·색·윤기를 살린 **맛있어 보이는 실사풍**으로 그린다.
   - 고칠 곳: `concepts.ts:17,77`, `style.ts:47`, `openaiRequest.ts:219-221`.
2. **냄새·향 표현 금지 목록**: 보라·초록 연기, 찡그린 얼굴, 코 막는 동작처럼 혐오를 떠올리게 하는 표현을 막는다. 향은 '김이 오르는 따뜻한 김' 정도로만 그린다. `foodDirection()`(`openaiRequest.ts:39`)에 모든 화풍 공통으로 넣는다.
3. **음식 장은 실사로 고정**: 맛을 말하는 장과 결론 장은 콘셉트가 무엇이든 `drawn:false`(실사)로 코드에서 강제한다(`concepts.ts:94` `readConceptProposal`). 일러스트는 원리·비교·도식 장에만 쓴다.
4. **기본 선택을 '실사'로**: 콘셉트 화면의 기본값을 실사로 바꾸고, 일러스트는 사장님이 고를 때만 쓴다(`concepts/route.ts:26`).
5. **표지 검사 기준**: 표지 검사(`coverCheck.ts`)가 "의인화한 캐릭터"를 맞는 표지로 받아 주는 것을 고친다. 음식에 얼굴이 있으면 다시 그리게 한다.
6. **확인**: 홍어회, 홍어찜, 삼합 주제로 각 콘셉트를 2번씩 그려 사장님이 '맛있어 보이는지'를 보고 판정한다. 프롬프트 문장은 시험으로 고정한다.
